# Decomposition method: how a shot's production method is judged

Goal: for each shot, give the production method of the base picture, the overlays, the evidence and a confidence, then a remake route.

## 1. Labels

| Label | Meaning | Remake route (rea_video/capabilities/routing.yaml) |
|---|---|---|
| `live_action` | Live action | R07: AI image-to-video approximation, or reshoot |
| `ai_video` | AI-generated video | R07: first and last frames + prompt, generated by capsule-cinema |
| `avatar` | Digital avatar talking head | R03: voice clone + digital avatar |
| `cg_3d` | 3D render | R08: 3D modeling and rendering, or AI first/last-frame approximation |
| `code_render` | Code/template render (motion graphics, text, UI, charts, cards) | R01: Remotion/HTML rebuild |
| `screen_capture` | Screen recording/screenshot | R02: record the real interface |
| `still_motion` | Still image + pan and zoom | R17: one image + measured motion, reproduced exactly on the local machine |
| `static_hold` | Held frame | R18: one image |
| `anim_2d` | 2D animation | R19: set the character and style with an image model, then first/last-frame generation |
| `stop_motion` | Stop-motion | R20: shoot it frame by frame, or approximate with image-to-video |
| `film_footage` | Film, TV or short-drama footage cut in | R21: find and cut the matching source footage |

Overlays are listed separately: subtitles, titles, text callouts, graphic stickers, layout templates. One shot can be "AI video + code subtitles".

## 2. Where the evidence comes from

Deterministic forensics handles what can be measured, and the VLM handles what has to be understood:

| Question | Method | Reliability |
|---|---|---|
| Where are the cuts | HSV histogram distance and pixel difference with a locally adaptive threshold; the changed area must be large enough, so a popping element isn't a cut. Jump cuts / punch-ins: a one-frame jump from the same camera position, much larger than the change in surrounding frames, with stable frames on both sides; flashes and fire that brighten and recover within one or two frames aren't cuts. Cross dissolves: whether middle frames are a linear blend of the end frames, using optical flow to rule out push and pull. Transitions: each boundary gets a start and end, then is classified as fade / flash / dissolve / wipe / push / whip pan / zoom / rotate / blur / glitch / shake, with direction for wipes and pushes | High (F1 = 1.0 on two ground-truth videos, one with 14 dissolves of 0.25s) |
| Did the picture move | Share of pixel-identical repeated frames, first/last frame difference | High |
| Is it one image with pan and zoom | LK optical flow fitted to a similarity transform (RANSAC): high inlier ratio, low residual, no local motion, and almost nothing left after motion compensation | High |
| Rendered or photographed texture | Share of flat 8×8 blocks, colors needed to cover 95% of pixels, ratio of horizontal and vertical straight edges, Immerkær noise | High (separates renders from photos) |
| 2D compositing / code motion | Background pixels exactly unchanged frame to frame, with motion only in local areas | High |
| Original frame rate | Repeated-frame pattern (about 20% for 24→30, period 4–6); periodic sharpness changes from frame interpolation (weak evidence without repeated frames, since recompression can create it too); native ≥48 fps with no repeated frames | Medium-high: generation models output 24/25 fps, phones often shoot 60 fps |
| Live action, AI or 3D | Sensor and temporal noise, handheld shake, frame-rate fingerprints, plus VLM checks for flaws (fingers, text, physics, flickering texture) | Medium with deterministic evidence only, high with a VLM |
| Metadata | Capture device make/model; GB 45438 implicit AIGC labels (Label 1/2/3 and provider code); C2PA; editor/renderer signatures | Very strong when present; often stripped by platforms |
| Overlays | Edge clusters with frozen pixels over a moving background, plus OCR text tracks (position, whether it changes over time, whether it's horizontal) | Medium-high |
| Audio | Onsets/beats, share of cuts landing on onsets (beat sync), speech modulation features | Medium |

Segments joined by jump cuts come from the same footage (same camera position and background). With a VLM on, they are merged into one clip and asked about once (up to 12 seconds and 8 segments): production method and shooting style are answered once for the whole run, with a separate description and remake prompt per segment. When VLM calls are capped, the shots the tool is least certain about and the longest shots go first. Text on a shot comes straight from the whole-video OCR pass for that time range. Only when that pass is too sparse (long videos) or the packaging layer is off does it read 1–4 frames per shot based on duration.

## 2.1 Real user assets

Material sources fall into four kinds: AI-generated, rendered by the maker, real user assets, and mixed.

- **Full frame**: derived from the base picture label. Live action = live footage; screen capture = interface recording/screenshot; a held frame from a photo or screenshot = real asset.
- **Embedded** (detected only in rendered pictures):
  - A light, low-saturation panel with ≥6 small text areas in one frame → interface screenshot (confirmed real asset)
  - An area with high grayscale entropy and no flat color → image or video clip (real or AI **to be confirmed**)
  - The subtitle band is excluded from detection
- In the remake plan, real assets are listed in `user_assets`. The user provides them for the remake, and they can't be generated by a model.

## 2.2 Sound

HPSS on the STFT (median filtering to separate harmonic and percussive parts):

- **Voice**: 3–8 Hz syllable modulation in the voice band, plus pauses between lines; pitch gives a male/female hint. With several speakers, dry vocals are split by voice into one track per speaker.
- **Music**: a music bed that stays loud and tonal in the gaps between speech, or a clear beat period. BPM comes from onset autocorrelation, key from Krumhansl profiles, and section changes from chroma novelty.
- **Editing**: share of cuts landing on beats or onsets.
- **Sound effects**: the deterministic layer only offers prominent non-vocal transients as low-confidence candidates. The VLM provides the full list by listening (see measurements in eval/RESULTS.md).
- **Output**: `audio` (measurements), `audio_plan` (sound tracks and remake plan after merging the VLM), `audio.png` (timeline).

## 3. Fusion

Final probability ∝ deterministic probability^(0.6 × trust weight) × VLM probability, with two hard constraints:

- A shot with a frozen picture can't be labeled as any kind of video generation.
- A shot with rigid whole-image pan and zoom can't be labeled live action or digital avatar.

Trust weights: held frame 1.6, still pan and zoom 1.4, code render 1.0, and only 0.6 for live action, AI and 3D, so the VLM mostly decides those three.

When a visual source (VLM or agent review) takes part, the judgment has two steps. First decide how the picture came to be (generated: AI video + digital avatar; rendered: 3D + code; live action; screen recording; still image), then pick the specific label within that group. Confidence is the total probability of the group. So when "the tool says AI video, the agent says digital avatar, the VLM says live action", the first two votes count together as "generated" instead of being split and beaten by a strong "live action". With the tool alone it still takes the top specific label: the tool's avatar score is carved out of AI video, so merging them would outweigh live action (on the talking-head eval set, the measured result drops from 0.51 to 0.33).

Majority rule: when the tool's top pick agrees with exactly one of the two visual sources (same label, or same group), the verdict must stay in that group.

Other checks:
- When the tool and VLM disagree on live action vs not, and no agent has reviewed it, the shot is marked "disputed" and goes on the must-review list in `review_tasks.json`. VLMs can invent evidence that isn't visible (for example, "garbled wall clock digits" in the juicer source).
- Frame rate only says the footage has a 24 fps source: when a shot is labeled AI video with no AIGC label and the visual source says live action, it's marked "AI or 24p camera footage, to be confirmed", with confidence capped at 0.7.
- Text read by OCR that isn't in the VLM's list of post-production text (or that moves with an object in the picture) counts as text on an object, not an overlay.

## 4. Output

```
out/<name>/
  breakdown.json   Video IR (rea_video.breakdown.v1): features, evidence, probabilities, overlays and remake plan per shot
  report.html/md   Human-readable report (same content; HTML is rendered from Markdown): verdict → content and structure (summary, hook, structure timeline, script) → characters, scenes and props →
                   sound (one card each for voice / music / effects / ambience) → shooting, lighting and editing → editing and packaging layer → remake plan (with real asset and reference lists) →
                   shot list → uncertain points → appendix (folded per-shot evidence, metadata). Characters, scenes, props and script come from whole-video VLM analysis or agent review (top-level cast in review_answers.json)
  storyboard.jpg   Storyboard overview (colored by production method)
  shots/           Contact sheet, first frame and last frame per shot (first and last frames are also remake inputs)
  clips/, vlm_cache/  VLM input clips and cache (--vlm only)
```

`finalize()` can reclassify from saved features and VLM answers alone: after a rule change there's no need to decode the video again, and `rea-video eval` does this automatically.
